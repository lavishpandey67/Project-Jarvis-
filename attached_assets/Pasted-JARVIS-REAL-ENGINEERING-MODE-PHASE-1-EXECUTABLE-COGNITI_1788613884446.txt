PHASE 1A — EXECUTION GRAPH
==================================================

Implement a genuine runtime representation of execution state.

The system must have explicit concepts for:

- execution/task identity
- goal
- current state
- graph/node identity
- transition
- node input
- node output
- execution result
- observation
- failure
- retry/recovery
- termination
- evidence
- timestamps
- correlation/execution IDs

The graph must support conditional transitions based on REAL
execution state and REAL observations.

The model may propose what should happen.

The deterministic runtime must decide whether a transition is
actually allowed.

Do not allow free-form model text to silently control execution.

==================================================
PHASE 1B — REAL EXECUTION
==================================================

Connect the graph to the EXISTING real tools.

The graph must be capable of invoking actual repository operations,
including where appropriate:

- file inspection
- file modification
- patching
- test execution
- build execution
- runtime/process verification

Every action must produce structured execution evidence.

For example:

- command executed
- exit code
- stdout/stderr where appropriate
- files changed
- before/after hashes where available
- execution duration
- tool identity
- state transition
- failure information

Never fabricate these values.

==================================================
PHASE 1C — FAILURE + RECOVERY
==================================================

A failed operation must create an explicit failure state.

The system must distinguish at least:

SUCCESS
FAILURE
RECOVERABLE_FAILURE
UNRECOVERABLE_FAILURE
CANCELLED
ESCALATED

Implement bounded recovery.

Do NOT create an infinite self-correction loop.

A recovery attempt must be based on actual observations from the
failed execution.

If recovery fails beyond the configured boundary:

→ stop
→ preserve evidence
→ report failure honestly

Never convert failure into success merely because the model says
the task should now work.

==================================================
PHASE 1D — VERIFICATION
==================================================

Define objective completion criteria.

Completion must require evidence satisfying those criteria.

Example:

"Build succeeded" is not equivalent to:

"the model predicted that the build should succeed."

Use actual process/test/runtime evidence.

The evaluator must receive:

- original objective
- expected success criteria
- execution history
- observations
- final state

and return a structured evaluation.

==================================================

- retry

- transactional state changes

Do not introduce a new database merely because it is fashionable.
